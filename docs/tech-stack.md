# Утверждённый стек и архитектура

Статус: утверждено заказчиком 15 октября 2026 года в текущем чате сообщением «Утверждаю» после обсуждения стека и уточнений требований к коду и документации.

Это целевое техническое решение. Приложение, инфраструктура и компоненты пока не созданы. Изменение утверждённого решения требует согласования.

## Backend

| Область | Решение |
| --- | --- |
| Платформа | .NET 10 LTS, ASP.NET Core 10 |
| API | Minimal APIs, группировка endpoints по фичам, OpenAPI, единый формат ошибок Problem Details |
| Сценарии | MediatR: команды, запросы и pipeline behaviors для валидации и логирования |
| Валидация | FluentValidation 12 |
| Доступ к данным | EF Core 10, Npgsql 10, миграции в репозитории |
| База данных | PostgreSQL 18 |

Заказчик допускает использование лицензии MediatR, включая коммерческую, если она потребуется. Конкретную стабильную версию и подходящую лицензию фиксируем при подключении зависимости; это согласование не означает покупку лицензии.

## Архитектура

Основа — модульный монолит с Clean Architecture и Vertical Slice, отдельное React-приложение. Границы бизнес-модулей определяем по требованиям продукта; их зависимости контролируем архитектурными тестами.

Clean Architecture задаёт направление зависимостей:

| Слой | Ответственность и зависимости |
| --- | --- |
| Domain | Сущности, бизнес-правила, доменные события. Не зависит от остальных слоёв и инфраструктуры |
| Application | Сценарии, команды и запросы MediatR, валидаторы, интерфейсы хранения и внешних сервисов. Зависит от Domain |
| Infrastructure | Реализация интерфейсов Application: EF Core, PostgreSQL, доступ к сайтам и внешним системам. Зависит от Application и Domain |
| API | HTTP-контракты, endpoints и сборка приложения через DI. Вызывает Application; подключает Infrastructure в точке настройки зависимостей |

Vertical Slice задаёт организацию сценариев внутри этих границ. Например, `Checks/StartCheck` объединяет команду, обработчик, валидатор и результат; `Checks/GetReport` — другой сценарий. Это примеры структуры, а не утверждённые продуктовые фичи. Общие бизнес-правила остаются в Domain, детали инфраструктуры — в Infrastructure.

Не создаём универсальные CRUD-репозитории и общие сервисы без конкретной потребности. API остаётся тонким, правила сценариев не дублируются в endpoints.

## Тестирование и эксплуатация

- Backend: xUnit, интеграционные тесты через WebApplicationFactory и Testcontainers с PostgreSQL; архитектурные тесты границ зависимостей.
- Frontend: Vitest и React Testing Library.
- E2E: Playwright с frontend и backend.
- Локальное окружение: Docker Compose.
- CI: GitHub Actions; сборка, статический анализ, проверка типов и тесты по мере появления соответствующих частей проекта.
- Наблюдаемость: структурированные логи и OpenTelemetry.
- Версии SDK, инструментов и зависимостей фиксируем при создании приложения; lock-файлы храним в репозитории. Перед подключением проверяем совместимость и актуальные стабильные патчи согласованных основных версий.

## Решения, отложенные до сбора требований

Фоновые проверки и способ их выполнения не являются частью этого выбора стека. Очередь, планировщик, отдельные процессы и другие механизмы фоновой обработки пока не выбраны.

Также отдельно определим продуктовые сценарии, авторизацию, границы модулей, нагрузку, эксплуатационные параметры и требования публичных страниц к SEO/SSR. Эти вопросы не отменяют обязательных [требований к коду](code-standards.md) и [документации](documentation.md).
