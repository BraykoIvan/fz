# Описание проекта

## Назначение

Создать сервис проверки сайтов на соответствие применимым требованиям Роскомнадзора и федеральных законов РФ. Конкретный перечень нормативных актов, условий применимости и автоматических проверок предстоит согласовать.

## Текущее состояние

- Подготовлена структура репозитория: `AGENTS.md`, `docs/`, `src/`.
- Зафиксирован обязательный процесс разработки.
- Утверждены [стек и архитектура](tech-stack.md), [требования к коду](code-standards.md) и [документации](documentation.md).
- Продуктовый функционал и дизайн пока не созданы; утверждённая архитектура ещё не реализована.
- Реализованные проверки и тесты отсутствуют.

## Подтверждённые требования к процессу

1. Изучить текущий функционал, полностью собрать и уточнить требования с заказчиком, получить согласование.
2. Для существенных изменений UI создать дизайн-борд фичи в Stitch через Stitch MCP, согласовать дизайн и изучить его HTML/CSS. Для небольших изменений или задач без изменений UI создание дизайна необязательно.
3. Полностью реализовать frontend и backend, добавить unit-, integration- и e2e-тесты.
4. Подтвердить реализацию всех бизнес-требований и полное соответствие согласованному дизайну в Stitch, если он есть. Результаты проверок указать в PR.
5. Каждую задачу выполнять в отдельной ветке и сливать в `main` через Pull Request после зелёного пайплайна. После слияния переключаться на `main` и обновлять её.
6. Соблюдать DRY и KISS, готовность backend к сбоям и горизонтальному масштабированию, использовать дизайн-систему Stitch и shared-компоненты frontend со Storybook.
7. Документировать все API и фоновые процессы с Mermaid-диаграммами последовательностей; поддерживать OpenAPI-контракты в актуальном состоянии.

Подробные правила приведены в [workflow.md](workflow.md).

## Открытые вопросы для этапа сбора требований

Это вопросы для исследования, а не согласованный объём продукта.

- Кто пользуется сервисом, какие задачи решает и как выглядит успешная проверка?
- Какие категории сайтов, владельцев и пользователей входят в область проверки?
- Какие нормативные акты и требования применимы, по каким условиям определяется применимость?
- Какие проверки можно автоматизировать, где требуется ручная или экспертная оценка?
- Как задаётся сайт и каковы границы обхода: страницы, поддомены, динамический контент, авторизация?
- Какие доказательства, объяснения, рекомендации и форматы отчёта нужны пользователю?
- Какие состояния результата нужны для ошибок доступа, неполных данных и неоднозначных выводов?
- Нужны ли аккаунты, роли, история проверок, повторные проверки и интеграции?
- Каковы требования к нагрузке, длительности проверки, доступности, хранению данных и безопасности?
- Где будет работать сервис и какие ограничения есть для инфраструктуры в рамках утверждённого стека?
- Как будут реализованы фоновые проверки? Это решение отложено и не входит в утверждённый выбор стека.

## Правовые проверки

До реализации каждой проверки нужно зафиксировать официальный источник и его редакцию, дату проверки актуальности, условие применимости, проверяемый признак, допустимые результаты и ограничения автоматизации. Нельзя делать вывод о полном соответствии сайта законодательству только по отсутствию найденных автоматикой нарушений.

Согласованные требования и критерии приёмки первой фичи будут сохранены в `docs/features/<feature-id>/requirements.md`. Список нормативных актов в этом документе намеренно не задан до исследования применимости.
