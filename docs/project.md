# Описание проекта

## Назначение

Создать сервис проверки сайтов на соответствие применимым требованиям Роскомнадзора и федеральных законов РФ. Конкретный перечень нормативных актов, условий применимости и автоматических проверок предстоит согласовать.

## Текущее состояние

- Подготовлена структура репозитория: `AGENTS.md`, `docs/`, `src/`.
- Зафиксирован обязательный процесс разработки.
- Утверждены [стек и архитектура](tech-stack.md), [требования к коду](code-standards.md) и [документации](documentation.md).
- Согласованы аудитория, основные решения бесплатного MVP и первый набор проверок; см. [требования](features/site-audit/requirements.md) и [решения](features/site-audit/decisions.md).
- Подготовлен отдельный [каталог потенциальных нарушений](violations.md) для постепенного включения проверок. Каталог и методики ещё требуют правовой детализации.
- Подготовлен [план работ по MVP](mvp-plan.md): 22 задачи с зависимостями и критериями готовности; первые 6 — болванка приложения с фейковой проверкой для оценки UI/UX. Реализация задач ещё не начата.
- Продуктовый функционал и дизайн пока не созданы; утверждённая архитектура ещё не реализована.
- Реализованные проверки и тесты отсутствуют.

## Подтверждённые требования к процессу

1. Изучить текущий функционал, полностью собрать и уточнить требования с заказчиком, получить согласование.
2. Для существенных изменений UI создать дизайн-борд фичи в Stitch через Stitch MCP, согласовать дизайн и изучить его HTML/CSS. Для небольших изменений или задач без изменений UI создание дизайна необязательно.
3. Полностью реализовать frontend и backend, добавить unit-, integration- и e2e-тесты.
4. Подтвердить реализацию всех бизнес-требований и полное соответствие согласованному дизайну в Stitch, если он есть. Результаты проверок указать в PR.
5. Каждую задачу выполнять в отдельной ветке и сливать в `main` через Pull Request после зелёного пайплайна. После слияния переключаться на `main` и обновлять её.
6. Соблюдать DRY и KISS, готовность backend к сбоям и горизонтальному масштабированию, использовать дизайн-систему Stitch и shared-компоненты frontend со Storybook.
7. Документировать все API и фоновые процессы с Mermaid-диаграммами последовательностей; поддерживать OpenAPI-контракты в актуальном состоянии.

Подробные правила приведены в [workflow.md](workflow.md).

## Согласованный первый этап: UI/UX-прототип

По прямому уточнению заказчика сначала создаём работающее приложение на утверждённом стеке с фейковой проверкой. Оно позволяет ввести URL, увидеть ожидание и демонстрационные находки/санкции/ТЗ, скачать образец PDF, оценить основные состояния интерфейса. Для существенного UI необходимы Stitch MCP и согласование дизайна; shared-компоненты подготавливаются для дальнейшего использования.

Данные явно обозначаются как демонстрационные; введённый сайт не сканируется. Прототип не требует готового правового движка, настоящего общего лимита/хранения 24 часа или промышленной генерации PDF. После оценки и согласования UI/UX реализуем настоящий аудит с переиспользованием интерфейса. Конечные требования ниже сохраняются.

## Подтверждённые решения MVP

- Пользователь — владелец любого сайта в РФ; применимость требований зависит от деятельности, а не только доменной зоны.
- На первом этапе всё бесплатно, без регистрации и без ИИ.
- Результат — обязательный PDF с находками, диапазонами потенциальных штрафов, ссылками на действующие нормы и полным ТЗ по исправлению каждой проблемы.
- Обход — до 20 HTML-страниц плюс найденные правовые документы. Выполнение JavaScript отложено.
- Один общий результат на сайт в течение 24 часов с момента запуска; повторные запросы возвращают сохранённые данные. `www` и основной hostname объединяются, остальные поддомены — отдельные сайты.
- После технической ошибки без отчёта разрешён повторный запуск.
- Проверка любого публичного сайта разрешена без подтверждения владения. Публичного каталога и индексации отчётов нет; результаты и PDF доступны и хранятся только в пределах 24 часов от запуска.
- Входные правовые документы — HTML и текстовые PDF; неподдерживаемые форматы внутренне отмечаются как непроверенные и не входят в пользовательский результат.
- Частичные ошибки не входят в результат. Запуск считается успешным; пользователю показывается только то, что удалось проверить. Диагностика пропусков остаётся внутри сервиса.
- Диапазоны санкций — по категориям лиц, без неподтверждённого сложения и догадок о повторности.
- Начальный набор: доступность политики ПДн и сведений о защите, признаки отдельного согласия в HTML-формах и предустановленные отметки. Все остальные проверки включаются постепенно через каталог.

## Открытые вопросы для этапа сбора требований

Не пересогласовывай уже подтверждённые решения. Дальнейшая техническая детализация перечислена в [требованиях MVP](features/site-audit/requirements.md): удаление служебных данных, лимиты и внешние ссылки документов, эксплуатационные параметры и полная правовая методика. Доступ к общему результату, оба срока 24 часа от запуска, частичные ошибки и форматы HTML/текстовый PDF уже согласованы. Способ фоновой обработки остаётся отдельным техническим решением.

## Правовые проверки

До реализации каждой проверки нужно зафиксировать официальный источник и его редакцию, дату проверки актуальности, условие применимости, проверяемый признак, допустимые результаты и ограничения автоматизации. Нельзя делать вывод о полном соответствии сайта законодательству только по отсутствию найденных автоматикой нарушений.

Требования первой фичи и критерии приёмки сохранены в [requirements.md](features/site-audit/requirements.md). Карта нормативных актов, источников и ограничений проверки — в [каталоге](violations.md). Успешная сверка официальной действующей редакции обязательна перед включением правила в продукт.
