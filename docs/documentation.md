# Требования к документации

Статус: утверждено заказчиком 15 октября 2026 года сообщением «Утверждаю» в текущем чате после уточнения требований к API и фоновым процессам.

## Общие правила

- Храни документацию проекта в `docs/`, поддерживай навигацию в [README.md](README.md).
- Документируй все API и фоновые процессы. Новая или изменённая реализация должна сопровождаться актуальной документацией в том же PR.
- API-контракты описывай через OpenAPI. Поведение и взаимодействия участников описывай в Markdown с Mermaid-диаграммами последовательностей, используя блоки `mermaid` с `sequenceDiagram`.
- Для нового API или фонового процесса отсутствие документации и диаграммы последовательности означает, что задача не готова.
- Не представляй запланированное поведение как реализованное. Фиксируй ограничения, условия применимости и открытые вопросы явно.
- Не включай секреты, реальные персональные данные и чувствительные данные проверяемых сайтов в примеры и диаграммы.

## API

Для каждого endpoint укажи:

1. Назначение и связанный пользовательский сценарий.
2. HTTP-метод, путь, авторизацию и необходимые права.
3. Параметры, тело запроса, ограничения и правила валидации.
4. Ответы: статусы, схемы, примеры, ошибки Problem Details и значимые причины ошибок.
5. Изменения данных, бизнес-инварианты, транзакционные границы, поведение при повторных и конкурентных запросах — где применимо.
6. Mermaid-диаграмму последовательностей: участники, вызовы, доступ к хранилищам и внешним системам, ответ клиенту, существенные альтернативные пути.

Рекомендуемое расположение: `docs/api/<module>.md`. Каждый endpoint должен быть явно связан с описанием и диаграммой. Общую диаграмму можно переиспользовать для нескольких endpoints, если она точно отражает каждый из них, а различия описаны.

Не переписывай вручную схемы, уже определённые в OpenAPI: давай ссылку на соответствующую операцию или контракт. При наличии генерации из кода проверяй, что итоговая спецификация отражает реальный контракт и включена в проверку изменений API.

## Фоновые процессы

Для каждого процесса укажи:

1. Назначение и условия запуска: событие, расписание или ручной запуск согласно выбранной реализации.
2. Входные данные, этапы работы, участников и зависимости.
3. Сохраняемые состояния, изменения данных, результаты и условия завершения.
4. Обработку ошибок, ограничения времени, отмену, повторы, идемпотентность и восстановление после сбоя — где применимо. Явно отмечай неприменимые пункты.
5. Поведение при параллельном выполнении на нескольких экземплярах и гарантии консистентности.
6. Доступные средства наблюдения и диагностики по мере реализации: логи, метрики и трассировки.
7. Mermaid-диаграмму последовательностей, показывающую запуск, выполнение, сохранение результата и существенные ветви ошибок или восстановления.

Рекомендуемое расположение: `docs/processes/<process-id>.md`. Эти правила применяются при появлении процессов и не определяют заранее способ их реализации.

## Диаграммы последовательностей

Используй понятные имена участников и операции, соответствующие реальной реализации. Для альтернативных путей используй `alt`/`else`, для необязательных действий — `opt`, для повторов — `loop`, когда это помогает понять сценарий. Отражай границы транзакций и момент фиксации, если они важны для корректности.

Проверяй синтаксис и читаемость диаграмм в Mermaid-совместимом просмотрщике. При изменении сценария обновляй диаграмму вместе с текстом и OpenAPI. Диаграмма должна объяснять последовательность взаимодействий; перечисления компонентов или схема слоёв её не заменяют.
