# План работ: сначала UI/UX-прототип, затем MVP

Дата: 15 октября 2026 года. Статус: сначала нужна болванка приложения с фейковой проверкой для оценки UI/UX. По поручению заказчика выполняется MVP-001: [сценарии и дизайн](features/ui-ux-prototype/design.md); реализация приложения ещё не начата.

Основания: [требования MVP](features/site-audit/requirements.md), [решения заказчика](features/site-audit/decisions.md), [каталог проверок](violations.md), [стек](tech-stack.md), [стандарты кода](code-standards.md), [документация](documentation.md), [workflow](workflow.md).

## Два результата и порядок их получения

**Этап А — приложение для оценки UI/UX.** Рабочие экраны на утверждённом стеке, shared-компоненты из дизайн-системы Stitch и фейковая проверка. Пользователь проходит весь сценарий: ввод URL → ожидание → демонстрационный результат → скачивание демонстрационного PDF. Заказчик оценивает интерфейс и взаимодействия до разработки настоящего сканера.

Для этого этапа прямо разрешены подготовленные фикстуры и симуляция проверки. В интерфейсе и PDF они обозначены как демонстрационные данные; запросы к введённому сайту не выполняются. Фейковые находки, суммы и тексты служат оценке представления информации, а не юридическому выводу. Готовность прототипа не означает готовность проверок, общего лимита, надёжного хранения и удаления данных настоящего сервиса.

**Этап Б — рабочий MVP.** После оценки и согласования UI/UX подготовленный интерфейс подключается к реальному обходу, четырём правовым проверкам и формированию отчёта. Общие UI-компоненты, контракты и представление результата переиспользуются; прототип не выбрасывается целиком.

Для настоящего MVP сохраняются все [BR-001–BR-020](features/site-audit/requirements.md): бесплатно, без регистрации и ИИ; до 20 HTML-страниц плюс документы HTML/текстовый PDF, без выполнения JS; один общий результат на сайт и хранение 24 часа от запуска; `www` объединяется с основным hostname, остальные поддомены отдельно. После полного сбоя разрешён повтор. Частичные ошибки не входят в результат, пользователю показывается только выполненное.

Реальные проверки первого релиза — **PD-001, PD-002, PD-005, PD-006**. PDF содержит факты, доказательства, действующие правовые основания, условные диапазоны санкций по категориям лиц без неподтверждённого сложения и полное ТЗ по исправлению. Остальные правила каталога, аккаунты, оплата, ИИ, JS-сканирование, мониторинг по расписанию и публичный каталог отчётов остаются за пределами MVP.

## Этап А. Болванка приложения и оценка UI/UX

### MVP-001. Подготовить и согласовать сценарии и дизайн в Stitch

**Результат:** два простых макета через Stitch MCP — ввод адреса и результат проверки; согласованное визуальное направление, ссылки/ID и изученный HTML/CSS в документации.

**Работы:** по последнему уточнению заказчика начать дизайн заново и ограничиться 1–2 понятными экранами. Показать основной путь, находку и исправление, категории санкций и действие скачивания PDF на демонстрационных данных. Отдельные доски компонентов, мобильные артборды и макет PDF сейчас не создавать; остальные состояния проработать в задачах реализации прототипа. Не ждать окончательной правовой методики.

**Готово, когда:** заказчик согласовал конкретные два макета, HTML/CSS получены и изучены; пользователь сразу понимает ввод адреса, результат и дальнейшие действия. Нет регистрации, оплаты и вывода частичных технических ошибок; демонстрационный характер данных обозначен. Прежний отклонённый дизайн не используется.

### MVP-002. Создать болванку React/ASP.NET Core, окружение и CI

**Результат:** запускаемый React/TypeScript/Vite frontend и минимальный ASP.NET Core backend, базовая структура Clean Architecture/Vertical Slice, локальное окружение и GitHub Actions.

**Работы:** подключить необходимые части утверждённого стека, DI/MediatR, настройки, Problem Details, инструменты качества, фиксацию версий и инструкции запуска. Подготовить конфигурацию PostgreSQL для дальнейшей реализации; не создавать заранее полную модель настоящего аудита. Настроить сборку, проверку типов/анализа и запуск реальных тестов по мере их появления.

**Готово, когда:** приложение воспроизводимо запускается и frontend обращается к backend; CI выполняет доступные проверки без фиктивных тестов. Секреты не попали в репозиторий. Для каркаса не понадобились выбор очереди, исполнитель сканирования или правовая методика.

### MVP-003. Подготовить дизайн-систему, shared UI и Storybook

**Результат:** токены Stitch, переиспользуемые компоненты на основе shadcn/ui и Storybook.

**Работы:** подготовить поле URL, кнопки, состояние ожидания, карточки выполненных проверок/находок, представление правовых ссылок, санкций и ТЗ, скачивание отчёта, сообщения полного сбоя и истечения срока. Реализовать только необходимые компоненты и их применимые состояния.

**Готово, когда:** default/hover/focus/active/disabled/loading/error/success показаны там, где применимы; адаптивность, клавиатура и видимый фокус проверены. Компоненты соответствуют Stitch и имеют осмысленные компонентные тесты. Их можно подключить к настоящим данным без переписывания оформления.

### MVP-004. Реализовать демонстрационную проверку и фикстуры API

**Результат:** минимальные API запуска, состояния и демонстрационного результата с управляемыми сценариями вместо реального обхода.

**Работы:** подготовить синтетические находки, доказательства, условные санкции и тексты ТЗ. Имитировать ожидание, успех с находками/без находок, существующий результат, полный сбой с повтором и истечение срока. Сделать сценарии детерминированными и воспроизводимыми без ожидания суток. Данные имеют форму, пригодную для будущего настоящего отчёта; frontend получает типы из OpenAPI.

**Готово, когда:** введённый URL не вызывает запросов к сайту, API возвращает только подготовленные данные, исключены реальные ПДн. Режим симуляции явно отделён от будущей реальной реализации без лишнего универсального фреймворка. Unit-/integration-тесты подтверждают сценарии; API документирован с OpenAPI и Mermaid-диаграммами последовательностей как демонстрационный. Демо не заявляет реальные гарантии общего лимита, хранения или восстановления.

### MVP-005. Собрать полный пользовательский сценарий на фейковых данных

**Результат:** работающее приложение для оценки UI/UX: URL → ожидание → демонстрационный результат → демонстрационный PDF.

**Работы:** соединить shared UI и демонстрационный API через TanStack Router/Query, формы и валидацию. Реализовать все согласованные состояния, понятное представление находок, санкций и полного ТЗ. Для оценки скачивания/чтения использовать подготовленный PDF с демонстрационными данными; создание промышленного генератора отложено до MVP-019.

**Готово, когда:** заказчик самостоятельно проходит сценарии и может скачать образец PDF. Демо-проверка не требует юридически проверенных правил и не обращается к проверяемому сайту. Нет регистрации, оплаты, ИИ и вывода частичных технических ошибок. E2E-тесты проходят по демонстрационным сценариям; визуально проверены экраны и образец PDF.

### MVP-006. Провести оценку UI/UX с заказчиком и доработать прототип

**Результат:** заказчик оценил приложение, замечания устранены, согласован UI/UX для подключения реальной проверки.

**Работы:** предоставить запускаемый прототип, инструкцию и способы воспроизведения сценариев. Проверить понятность ввода, ожидания, результата, санкций, ТЗ и PDF на согласованных размерах экрана. Обновить Stitch и код при изменении дизайна, зафиксировать решения в документации.

**Готово, когда:** заказчик подтвердил конкретную версию прототипа; нет незакрытых замечаний, влияющих на дальнейшую реализацию. Тесты и визуальное сравнение со Stitch подтверждают изменения. Закрыт только этап А; настоящий аудит и BR-001–BR-020 ещё не объявлены реализованными.

## Этап Б. Настоящая проверка и рабочий MVP

### MVP-007. Завершить технические требования и архитектуру настоящего сервиса

**Результат:** уточнённые требования и техническое решение с учётом согласованного прототипа.

**Работы:** определить лимиты документов/размеров/времени, внешние правовые ссылки, robots.txt, редиректы, порты, полное отсутствие выполненных проверок и истечение срока во время работы. Уточнить ресурсы/нагрузку пилота. Выбрать механизм исполнения, хранения PDF/доказательств и удаления, границы транзакций, восстановление и контроль конкуренции. Не предписывать заранее брокер, планировщик или отдельный worker.

**Готово, когда:** неоднозначности, влияющие на поведение, закрыты; решения не меняют согласованный объём без согласования. Описаны инварианты, состояние проверки и последовательности процессов, нет критичного состояния только в памяти экземпляра. Выбраны совместимые библиотеки HTML/PDF и подходящие лицензии.

### MVP-008. Подготовить правовые карточки четырёх правил

**Результат:** карточки PD-001, PD-002, PD-005, PD-006 с подтверждёнными источниками, методикой, диапазонами санкций и подготовленными текстами ТЗ.

**Работы:** успешно сверить официальные действующие редакции и даты вступления, применимость/исключения, наблюдаемые признаки, квалификацию и двойной учёт. Подготовить положительные, отрицательные и неоднозначные примеры. Заменить демонстрационные тексты на проверенные материалы для настоящего отчёта.

**Готово, когда:** выполнена полная карточка по [каталогу](violations.md) и согласована методика. Нет автоматического вывода «нет checkbox — нарушение» и приравнивания обычного согласия к обязательному письменному. Недоступность официального источника блокирует включение реального правила, но не прототип этапа А.

### MVP-009. Реализовать модель данных и уточнить реальные контракты

**Результат:** модель сайта/проверки/попытки/выполненного правила/находки/правового основания/PDF, миграции EF Core/PostgreSQL и реальные контракты.

**Работы:** развить минимальные контракты прототипа, отделить диагностику от пользовательских результатов, сохранить время начала/истечения и версии правил/ТЗ. Уточнить сценарии MediatR, OpenAPI, Problem Details и типы frontend. Не переносить ограничения демонстрационного хранения в настоящую систему.

**Готово, когда:** миграции применяются, данные покрывают согласованные состояния; реальные контракты и Mermaid-последовательности актуальны. Изменения контракта отражены в frontend; общие модели и UI переиспользованы.

### MVP-010. Реализовать настоящий запуск, общий лимит и повторное использование

**Результат:** атомарный запуск и общий учёт проверки в PostgreSQL вместо симуляции ограничения.

**Работы:** нормализовать hostname, IDN, `www`, протокол, путь/query/fragment по требованиям. Возвращать одну активную проверку или существующий результат в окне 24 часа; после полного сбоя разрешать повтор с контролем конкуренции.

**Готово, когда:** параллельные запросы разных пользователей/экземпляров получают одну проверку, перезапуск не сбрасывает лимит, граница окна однозначна. Unit-/integration-тесты проверяют нормализацию, конкуренцию и срок. API и документация отражают реальные гарантии.

### MVP-011. Реализовать безопасную загрузку публичных ресурсов

**Результат:** единый HTTP-загрузчик страниц и документов с согласованными ограничениями.

**Работы:** проверять адреса, порты, DNS и каждый редирект; исключить внутренние/служебные цели, ограничить объём, распаковку и время. Обработать отмену, HTTP-статусы и тип содержимого. Не отправлять формы и не обходить авторизацию.

**Готово, когда:** целевые тесты подтверждают публичный ресурс, запрещённую цель, редирект и ограничения. Защита не отключается ради страницы; исчерпывающая матрица отказов не требуется.

### MVP-012. Реализовать обход до 20 страниц и чтение документов

**Результат:** реальный ограниченный обход, поиск форм/правовых ссылок и извлечение HTML/текстовых PDF без JS.

**Работы:** соблюдать порядок и границы обхода, устранять циклы/дубликаты; документы учитывать отдельно от HTML-квоты. Сканы, неподдерживаемые форматы и технические ошибки сохранять только во внутренней диагностике.

**Готово, когда:** контролируемые фикстуры подтверждают лимит, дедупликацию, чтение PDF и пропуск неподдерживаемого документа. JS не выполняется; публичные сайты не используются как нестабильная зависимость тестов.

### MVP-013. Подготовить механизм правил и модель доказательств

**Результат:** минимальный механизм реальных включённых правил и результатов их выполнения.

**Работы:** связать ID каталога, версии карточки, страницы/формы, наблюдаемые факты, применимость и минимальные безопасные доказательства. Разделить выполненный отрицательный результат, неоднозначную квалификацию и технический пропуск.

**Готово, когда:** правила добавляются без дублирования общего кода и лишнего DSL. Ошибка одного правила не становится находкой или ложным «проверено». Unit-тесты подтверждают различия и версионирование.

### MVP-014. Реализовать PD-001 и PD-002: политика и сведения о защите

**Результат:** реальные проверки по согласованным карточкам с данными для отчёта и ТЗ.

**Работы:** найти ссылки, проверить доступность и сведения о защите, в том числе внутри политики. Отличать HTTP 404 прямой ссылки от технического таймаута; не требовать отдельный файл или универсальное число разделов без основания.

**Готово, когда:** примеры карточек проходят unit-/integration-тесты. Ограниченный обход не объявляется доказательством отсутствия документа на всём сайте; связанные правила не удваивают санкцию одного эпизода.

### MVP-015. Реализовать PD-005 и PD-006: согласия HTML-форм

**Результат:** реальные проверки статических форм с точным местом и фактом срабатывания.

**Работы:** определить относящиеся к согласию элементы, checked, подписи/ссылки и объединение подтверждений. Учитывать основание обработки и границы HTML; не смешивать согласие с выбором товара.

**Готово, когда:** корректная/некорректная/неоднозначная и JS-зависимая формы обработаны по методике; есть unit-/integration-тесты. Технические пропуски исключены из пользовательского результата, неподтверждённая квалификация не назначена.

### MVP-016. Формировать реальные находки, санкции и полное ТЗ

**Результат:** единая настоящая модель отчёта для интерфейса и PDF вместо демонстрационных данных.

**Работы:** объединять связанные факты, выбирать проверенные нормы и условные санкции по категориям лиц. Формировать ТЗ из подготовленных шаблонов: URL/формы, действия, сведения владельца, ожидаемые изменения, критерии приёмки. Сохранять версии, не использовать ИИ.

**Готово, когда:** тесты подтверждают дедупликацию, полноту ТЗ и правильный выбор профилей. Нет сложения неподтверждённых штрафов, вымышленных реквизитов, сумм без оснований или частичных ошибок в пользовательской модели.

### MVP-017. Соединить настоящий процесс проверки и восстановление

**Результат:** рабочий путь от принятого запуска до сохранённого отчёта по настоящему обходу и четырём правилам.

**Работы:** подключить выбранное исполнение, состояния, владение работой, ограниченные повторы и восстановление. Полный сбой допускает новый запуск, частичный оставляет успешный результат только по выполненным проверкам.

**Готово, когда:** нет зависимости от демонстрационного исполнителя, перезапуск не дублирует активную работу. Integration-тесты подтверждают успех, частичный пропуск, полный сбой с повтором и один критический сценарий восстановления; все сочетания отказов не требуются. Процессы документированы с Mermaid-последовательностями.

### MVP-018. Реализовать доступность и удаление через 24 часа

**Результат:** настоящая политика срока для API, результатов, доказательств и файлов, механизм очистки.

**Работы:** прекратить выдачу через 24 часа от запуска независимо от задержки очистки; удалять данные/артефакты и обрабатывать гонку завершения/истечения. Минимальные служебные записи не дают доступ к старому отчёту.

**Готово, когда:** тесты с управляемыми часами подтверждают границу, удаление, недоступность старой ссылки и возможность нового запуска. Общая политика действует также для PDF, кешей и выбранного хранилища; диагностика и очистка документированы.

### MVP-019. Формировать и выдавать настоящий PDF-отчёт

**Результат:** динамический PDF из той же модели, что использует интерфейс, вместо подготовленного демонстрационного файла.

**Работы:** переиспользовать оценённую структуру/оформление; подставлять реальные проверки, доказательства, правовые ссылки, санкции и полное ТЗ. Обеспечить русский текст, ссылки, переносы и разбиение страниц. Повторять генерацию из сохранённых данных без нового обхода, соблюдать срок.

**Готово, когда:** короткий, длинный, пустой по находкам и частично выполненный отчёты визуально проверены после рендера без обрезания. Integration-тесты подтверждают содержимое, скачивание и отказ после срока. Каждая находка имеет ТЗ; частичные ошибки не показаны.

### MVP-020. Подключить готовый UI к настоящей проверке

**Результат:** согласованный на этапе А интерфейс работает с настоящим backend и PDF.

**Работы:** заменить источник демонстрационных данных реальными сценариями через сохранённые контракты. Проверить состояние ожидания, общий результат, повтор после полного сбоя, истечение срока и скачивание. Изменения дизайна согласовать в Stitch; не переписывать без причины shared UI.

**Готово, когда:** основной путь проходит e2e с настоящей проверкой на контролируемом сайте. В рабочем режиме нет фейковых данных или обращения к демонстрационным endpoints. Частичные ошибки скрыты, состояния соответствуют оценённому UI/UX, нет регистрации/оплаты/ИИ и индексации отчётов.

### MVP-021. Подготовить эксплуатацию и окружение пилота

**Результат:** развёртываемое окружение и инструкции сопровождения в пределах выбранных ресурсов.

**Работы:** настроить HTTPS, секреты, ограничения, структурированные логи/OpenTelemetry, проверку работоспособности, удаление артефактов и восстановление служебного состояния. Не помещать реальные ПДн и отчёты в логи; учитывать 24 часа во всех копиях/хранилищах. Описать миграции, диагностику и откат.

**Готово, когда:** окружение воспроизводимо поднимается, перезапуск/масштабирование не сбрасывают общий лимит, восстановление не возвращает пользователю истёкшие отчёты. Демонстрационный режим отделён от рабочего. Проведён минимальный эксплуатационный прогон.

**Работы:** прогнать созданные unit/integration/e2e и дополнить выявленные пробелы. Проверить реальные находки, отсутствие находок, частичный успех без вывода ошибок, общий результат, полный сбой/повтор, срок и PDF. Сравнить UI со Stitch, устранить дефекты и проверить актуальность API/процессов/OpenAPI/Mermaid.

**Готово, когда:** все критерии выполнены, проверки последнего коммита зелёные, документация актуальна; симуляция не подменяет приёмку настоящего сканера. После слияния последнего PR локальная `main` обновлена. Фактический запуск фиксируется после проверки опубликованного рабочего окружения.

## Правила исполнения

- Начинать с этапа А. Правовые карточки и промышленная инфраструктура не являются зависимостями прототипа; переход к настоящей реализации — после оценки UI/UX в MVP-006.
- Каждая задача — отдельная ветка и PR. Завершение фиксировать после выполнения критериев, проверок и слияния; после слияния вернуться на `main` и обновить её через `git pull --ff-only origin main`.
- Демо-данные прямо разрешены только для оценки UI/UX. Их использование документировать; не выдавать за настоящие проверки или готовый рабочий MVP. Граница между демонстрационной и реальной реализацией должна позволять переиспользовать UI и модель представления.
- Тесты и документацию добавлять вместе с соответствующей реализацией, включая демонстрационные API. Для всех API и процессов — OpenAPI и Mermaid-диаграммы последовательностей по правилам проекта. Результаты проверок сохранять в PR, отдельный файл отчёта не создавать.
- Соблюдать DRY/KISS, переиспользовать библиотеки, токены, shared UI, контракты и оформление PDF. Не создавать заранее сложное исполнение, универсальные движки или несогласованные функции.
- По факту обновлять статусы и ссылки на PR; при нескольких PR явно выделять подзадачи. MVP-001 остаётся незавершённой до явного согласования конкретной версии дизайна. Утверждение прототипа, дизайна и настоящей правовой методики — разные результаты.
