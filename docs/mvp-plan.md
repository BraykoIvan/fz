# План работ по MVP

Дата: 15 октября 2026 года. Статус: рабочая декомпозиция согласованного объёма; задачи реализации ещё не начаты. Этот документ задаёт порядок работ, зависимости и критерии готовности, а не меняет утверждённые требования.

Основания: [требования MVP](features/site-audit/requirements.md), [решения заказчика](features/site-audit/decisions.md), [каталог проверок](violations.md), [стек](tech-stack.md), [стандарты кода](code-standards.md), [документация](documentation.md), [workflow](workflow.md).

## Границы плана

Первый релиз: бесплатный сервис без регистрации и ИИ; любой публичный сайт без подтверждения владения; до 20 HTML-страниц и найденные правовые документы в HTML/текстовом PDF; без выполнения JavaScript.

Один результат общий для всех пользователей. `www` объединяется с основным hostname, остальные поддомены отдельно. Повторное использование и хранение результатов/PDF — 24 часа от запуска. После полного сбоя без отчёта повтор разрешён. Частичные технические ошибки не входят в пользовательский результат, запуск считается успешным; показываются только выполненные проверки.

Проверки первого релиза: **PD-001, PD-002, PD-005, PD-006**. В обязательном PDF — наблюдаемые факты, доказательства, ссылки на действующие нормы, условные диапазоны санкций по категориям лиц без неподтверждённого сложения и полное ТЗ для каждой проблемы. Будущие правила каталога не входят в покрытие MVP.

Не включать в этот план реализацию аккаунтов, оплаты, ИИ, браузерного сканера с JS, мониторинга по расписанию, генератора документов для установки на чужой сайт, дополнительных правовых проверок и публичного каталога отчётов. Внутренние API приложения обязательны; внешний клиентский API как отдельный продукт не входит в MVP.

Критические условия перехода:

- Правила и санкции не включаются в продукт до готовности MVP-002.

- MVP нельзя объявлять готовым до завершения MVP-020. Промежуточные результаты не выдаются за работающий пользовательский продукт.

## Задачи

### MVP-001. Завершить детали требований и параметры пилота

**Результат:** дополненные `requirements.md` и `decisions.md` без пересогласования уже утверждённых 20 бизнес-требований.

**Работы:** определить лимиты количества/размера документов, таймауты, внешние ссылки на правовые документы, редиректы и смену hostname, нестандартные порты, robots.txt и защиту от ботов. Определить поведение при полном отсутствии выполненных проверок и истечении срока во время выполнения. Уточнить бюджет, ресурсы пилота и ожидаемую нагрузку; согласовать решения, влияющие на пользовательское поведение или объём.

**Готово, когда:** для каждой границы есть однозначный результат; полный сбой отличается от частичного; ограничения не противоречат 20 страницам, бесплатности и общему окну 24 часа. Новые числовые значения записаны явно, а не скрыты в коде.

### MVP-002. Подготовить правовые карточки четырёх правил

**Результат:** карточки PD-001, PD-002, PD-005 и PD-006 в документации фичи, ссылки на них из каталога, подготовленные тексты рекомендаций и ТЗ.

**Работы:** успешно сверить официальные действующие источники, редакции и даты вступления; определить применимость и исключения, наблюдаемые признаки и допустимую квалификацию. Подготовить денежные профили по категориям лиц, сценарии повторности и правила устранения двойного учёта. Задать положительные, отрицательные и неоднозначные примеры, содержание полного ТЗ и критерии исправления без ИИ.

**Готово, когда:** у каждого правила есть полная карточка по [каталогу](violations.md), подтверждённый источник и согласованная методика. Отсутствие checkbox не объявляется автоматически нарушением; обычное согласие не приравнивается к обязательному письменному. Нет неподтверждённых сумм. Предыдущие таймауты официальных порталов не считаются успешной сверкой; недоступность источника блокирует включение соответствующего правила.

### MVP-003. Описать архитектуру выполнения и хранения

**Результат:** документированное техническое решение в рамках утверждённого стека.

**Работы:** определить структуру Clean Architecture и Vertical Slice, модель выполнения длительной проверки, устойчивое владение работой, восстановление после остановки и контроль конкуренции. Выбрать способ хранения PDF/доказательств, механизм удаления, границы транзакций, версии правил и контрактов. Выбрать библиотеки HTML/PDF с проверкой совместимости и лицензий, включая MediatR. Способ фоновой обработки выбрать здесь; брокер, планировщик или отдельный worker заранее не предписаны.

**Готово, когда:** описаны бизнес-инварианты и состояние проверки, момент начала окна, допустимые переходы, повтор после полного сбоя, отсутствие дублирующих активных работ при нескольких экземплярах, обработка истечения срока. Нет критичного состояния только в памяти экземпляра. Есть Mermaid-диаграммы последовательностей будущих процессов и план размещения в пилоте.

### MVP-004. Создать и согласовать дизайн-систему и макеты в Stitch

**Результат:** дизайн-борд через Stitch MCP, согласованная версия экранов и дизайн-системы; `design.md` со ссылками/ID и изученным HTML/CSS.

**Работы:** спроектировать ввод URL, ожидание проверки, повторное открытие существующего результата, выполненные проверки и находки, скачивание PDF, полный сбой с повтором, отсутствие находок, истёкший результат. Подготовить адаптивность, токены, shared-компоненты и состояния. Определить читаемую структуру PDF и её связь с экраном результата.

**Готово, когда:** заказчик согласовал конкретную версию; HTML/CSS получены и изучены. Нет регистрации, оплаты, скрытых платных результатов и вывода частичных технических ошибок. UI и формулировки не обещают проверку JS или всего законодательства. Состояние «нарушений не найдено» относится только к выполненным проверкам.

### MVP-005. Создать основу приложения, локальное окружение и CI

**Результат:** минимальный рабочий каркас backend/frontend в `src/`, PostgreSQL и локальное окружение, GitHub Actions, инструкции запуска.

**Работы:** настроить проекты и зависимости утверждённого стека, DI, EF Core/Npgsql, конфигурацию, базовые обработчики ошибок, React/TypeScript/Vite и инструменты качества. Добавить Docker Compose, фиксацию версий и lock-файлы. Подготовить запуск xUnit, интеграционных тестов с Testcontainers, Vitest/React Testing Library и Playwright по мере появления сценариев. Не добавлять неиспользуемые продуктовые модули и универсальные абстракции.

**Готово, когда:** окружение воспроизводимо поднимается по инструкции; backend/frontend собираются, проверки форматирования/анализа/типов запускаются в CI, архитектурные границы контролируются. Нет фиктивных тестов и ложного зелёного статуса для ещё не созданных проверок; новые реальные тесты подключаются к CI в своём PR. Секреты в репозиторий не попали.

### MVP-006. Определить модель данных и контракты приложения

**Результат:** модель сайта, проверки, попытки, выполненного правила, находки, правового основания и PDF; миграции и контракты запуска/состояния/результата/скачивания.

**Работы:** разделить пользовательские результаты и внутреннюю диагностику; сохранить время начала/истечения и версии методики/ТЗ. Описать сценарии MediatR, HTTP-контракты OpenAPI, Problem Details и типы для frontend. Минимальные служебные сведения не должны давать доступ к удалённым результатам.

**Готово, когда:** контракты покрывают согласованные состояния и данные отчёта, миграции применяются к PostgreSQL, TypeScript-типы генерируются из OpenAPI. Документы API и последовательностей описывают целевые контракты; при реализации каждого endpoint обновляются в том же PR.

### MVP-007. Подготовить shared UI и Storybook

**Результат:** необходимые для MVP компоненты shadcn/ui, адаптированные к дизайн-системе Stitch, и Storybook с их состояниями.

**Работы:** реализовать токены, поля URL, кнопки, блок состояния проверки, карточки выполненных проверок/находок, правовые ссылки, представление санкций и ТЗ, сообщения полного сбоя и истечения срока. Переиспользовать компоненты, не создавать каталог на гипотетическое будущее.

**Готово, когда:** применимые default/hover/focus/active/disabled/loading/error/success отражены в Storybook; клавиатурная навигация, фокус и адаптивность проверены. Компоненты визуально соответствуют Stitch, существенное поведение покрыто компонентными тестами.

### MVP-008. Реализовать запуск, общий лимит и повторное использование

**Результат:** сценарии запуска/получения состояния, нормализация адреса, общий учёт проверки в PostgreSQL; подключённый ввод URL и состояние ожидания на frontend.

**Работы:** объединять `www`/основной hostname, http/https, варианты регистра/IDN; исключать путь, query и fragment из ключа сайта. Прочие поддомены учитывать отдельно. Атомарно создавать одну проверку, возвращать существующую активную проверку или сохранённый результат в окне; после полного сбоя разрешать повтор с контролем конкуренции.

**Готово, когда:** параллельные обращения разных пользователей/экземпляров получают одну активную проверку; на границе 24 часов поведение однозначно. Перезапуск сервиса не сбрасывает лимит. Ошибки URL валидируются; технические внутренние состояния не раскрываются. Unit- и integration-тесты покрывают нормализацию, конкуренцию и границы окна. До готовности исполнителя задача не обозначается полноценным аудитом.

### MVP-009. Реализовать безопасное получение публичных ресурсов

**Результат:** один переиспользуемый HTTP-механизм загрузки для страниц и документов.

**Работы:** реализовать согласованные ограничения адресов, портов, DNS и редиректов; исключить обращения во внутреннюю сеть/служебные адреса, включая обход через смену DNS и редирект. Ограничить время, размер ответа и распаковку, обрабатывать отмену, HTTP-статусы и типы содержимого. Не отключать проверки безопасности ради получения страницы.

**Готово, когда:** загрузчик воспроизводимо получает публичные данные и отклоняет запрещённые цели на каждом переходе. Нет отправки форм/заявок и обхода авторизации. Целевые тесты проверяют разрешённый ресурс, запрещённую цель, редирект и таймаут/лимит размера; исчерпывающая матрица отказов не требуется.

### MVP-010. Реализовать ограниченный обход и чтение документов

**Результат:** обход до 20 HTML-страниц и извлечение доступного содержимого правовых HTML/текстовых PDF без JS.

**Работы:** определить начальную страницу и порядок обхода по согласованной политике, устранять дубликаты/циклы, находить правовые ссылки и формы. Документы учитывать отдельно от лимита HTML. Соблюдать параметры внешних документов, robots.txt, объёма и времени. Неподдерживаемые форматы, сканы и технические ошибки отмечать только внутри исполнения.

**Готово, когда:** лимит не превышается, документ не расходует HTML-квоту дважды, JS не выполняется. Детерминированные локальные фикстуры подтверждают обход, дедупликацию, чтение текстового PDF, исключение скана и обработку частичной ошибки. Публичные сайты не служат нестабильной тестовой зависимостью.

### MVP-011. Подготовить механизм правил и модель доказательств

**Результат:** минимальный расширяемый механизм запуска только включённых правил, результат выполненной проверки и внутренняя диагностика пропуска/ошибки.

**Работы:** связать ID каталога, версию карточки, проверенные страницы/формы, наблюдаемый факт, применимость и доказательства. Ограничить/обезличить сохраняемые фрагменты. Различать завершённую отрицательную проверку, неоднозначность квалификации и техническую невозможность выполнения.

**Готово, когда:** новое правило добавляется без дублирования общего кода, без универсального DSL на будущее. Ошибка одного правила не становится пользовательской находкой, ложным «проверено» или полным сбоем. Синтетические фикстуры и unit-тесты проверяют эти различия и версионирование.

### MVP-012. Реализовать PD-001 и PD-002: политика и сведения о защите

**Результат:** обе проверки по согласованным карточкам с данными для находок и ТЗ.

**Работы:** искать документы и ссылки из найденных мест сбора данных, проверять их доступность, учитывать сведения о защите внутри политики. Различать наблюдаемый HTTP 404 прямой ссылки и технический таймаут. Не требовать отдельный файл или универсальный набор разделов без основания.

**Готово, когда:** положительные, отрицательные и неоднозначные примеры из MVP-002 проходят; ограниченный обход не выдаётся за доказательство отсутствия документа на всём сайте. Одна проблема политики/доступа не удваивает санкцию из-за двух правил. Есть unit- и integration-тесты с HTTP/документными фикстурами и ссылки на реализацию в карточках.

### MVP-013. Реализовать PD-005 и PD-006: согласия HTML-форм

**Результат:** обе проверки статических HTML-форм по карточкам, с точным местом и фактом срабатывания.

**Работы:** определять относящиеся к согласию элементы, предустановленные отметки, текст подтверждения, ссылки и объединение согласия с иными документами. Учитывать законное основание и границы статического HTML, не смешивать checkbox выбора товара с согласием.

**Готово, когда:** примеры корректной формы, checked-согласия, объединённого подтверждения, нерелевантного checkbox и JS-зависимой формы обработаны по методике. Технические пропуски не показываются пользователю. Нет автоматической квалификации по составу обязательного письменного согласия без оснований; есть целевые unit-/integration-тесты.

### MVP-014. Сформировать итоговые находки, санкции и полное ТЗ

**Результат:** единая модель пользовательского отчёта для экрана и PDF, наполняемая фактическими результатами четырёх правил.

**Работы:** объединять связанные находки, выбирать правовые основания и условные профили санкций по категориям лиц. Формировать ТЗ из подготовленных шаблонов: затронутые URL/формы, действия, необходимые сведения владельца, ожидаемые изменения и критерии приёмки. Хранить версии текстов, не использовать ИИ.

**Готово, когда:** граждане/должностные лица/ИП/организации и условная повторность разделены; нет неподтверждённого сложения, вымышленных реквизитов или суммы при недостаточных основаниях. Частичные технические ошибки полностью исключены из модели пользователя, но не стирают внутреннюю диагностику. Unit-/integration-тесты проверяют дедупликацию, квалификацию и полноту ТЗ.

### MVP-015. Соединить полный процесс проверки и восстановление

**Результат:** рабочий путь от принятого запуска до сохранённого отчёта по реальному обходу, правилам и шаблонам.

**Работы:** подключить выбранный механизм исполнения, переходы состояний, контроль владения работой и ограниченные повторы. Сохранять результаты согласованно с общим окном. Обеспечить восстановление после перезапуска без дублирования активной работы. Полный сбой без результата допускает новый запуск; частичный сбой оставляет успешный результат только по выполненным проверкам.

**Готово, когда:** API возвращает настоящие данные без продуктовых заглушек; проверка другого сайта не блокируется одной зависшей работой. Интеграционные тесты проверяют успешную цепочку, частичный пропуск, полный сбой с повтором и один критический сценарий восстановления; не все комбинации отказов. Процесс документирован Mermaid-диаграммами в том же PR.

### MVP-016. Реализовать срок доступности и удаление через 24 часа

**Результат:** единая политика срока для API, данных, доказательств и файлов будущего PDF; работающий механизм очистки.

**Работы:** рассчитывать окончание от запуска, прекращать выдачу по всем маршрутам после срока независимо от задержки очистки, удалять бизнес-результаты и артефакты выбранным механизмом. Предусмотреть согласованную гонку завершения/истечения, недоступность старых ссылок и возможность следующего запуска. Механизм применять и к PDF при его подключении в MVP-017.

**Готово, когда:** локальные файлы/хранилище, API и кеширование не сохраняют доступ к старому отчёту. Служебные записи не позволяют его восстановить пользователю. Управляемые часы в тестах подтверждают границу срока, удаление и новый запуск; не нужно ждать сутки в тестах. Процесс очистки и сроки служебной диагностики документированы.

### MVP-017. Реализовать формирование и скачивание PDF

**Результат:** обязательный читаемый PDF на русском языке из той же модели отчёта, что использует приложение, и endpoint скачивания.

**Работы:** включить фактический объём выполненных проверок, находки, доказательства, правовые ссылки, категории санкций и полное ТЗ; не включать частичные ошибки и невыполненные проверки. Обеспечить шрифты, переносы, активные ссылки и разбиение страниц. Повторять генерацию из сохранённых результатов без нового обхода; сохранять файл по общей политике срока.

**Готово, когда:** короткий, длинный, пустой по находкам и частично выполненный отчёты читаются без обрезания текста/таблиц; каждый найденный пункт имеет ТЗ. Визуальная проверка отрендеренных страниц PDF обязательна. Integration-тесты подтверждают скачивание, содержимое и отказ после срока; повторная генерация не создаёт новую проверку сайта.

### MVP-018. Завершить пользовательский сценарий на frontend

**Результат:** согласованные экраны Stitch соединены с рабочим backend: ввод URL → состояние → результат → скачивание PDF.

**Работы:** использовать TanStack Router/Query, React Hook Form/Zod, сгенерированные типы API и shared UI. Показать существующий результат при повторном запросе, время его актуальности, полный сбой/повтор и истечение срока. Исключить частичные ошибки из пользовательских данных и состояний; не создавать каталог отчётов и индексацию.

**Готово, когда:** сценарий доступен без аккаунта/оплаты/ИИ и работает на согласованных размерах экрана с клавиатуры. Нет локальных имитаций результатов. Компонентные и e2e-тесты проверяют основной путь, повторное получение и значимые пользовательские состояния; сохранены сравнения со Stitch и исправлены расхождения.

### MVP-019. Подготовить эксплуатацию и окружение пилота

**Результат:** развёртываемое окружение, конфигурация, наблюдаемость и инструкции сопровождения в пределах выбранного бюджета.

**Работы:** настроить секреты, HTTPS, ресурсы и общие технические ограничения, структурированные логи/OpenTelemetry и проверку работоспособности. Не включать содержимое форм и PDF в технические логи. Настроить удаление артефактов, резервное копирование/восстановление служебного состояния с соблюдением согласованного срока хранения бизнес-результатов. Документировать развёртывание, миграции, диагностику и откат.

**Готово, когда:** окружение поднимается по инструкции, конфигурация соответствует согласованной нагрузке, перезапуск и масштабирование не сбрасывают лимит. Срок хранения учитывается во всех копиях и хранилищах, старые отчёты не возвращаются после восстановления. Есть проверяемые команды и минимальный эксплуатационный прогон; публикация внешнего окружения выполняется в согласованной для него процедуре.

### MVP-020. Провести итоговую приёмку MVP и подготовить запуск

**Результат:** проверка всех BR-001–BR-020, дизайна и эксплуатационной готовности; результаты в PR, исправленные дефекты и актуальная документация.

**Работы:** выполнить тесты уже созданных уровней и дополнить только выявленные пробелы. Пройти сквозные сценарии на контролируемых сайтах: находки, отсутствие находок в выполненных проверках, частичный успех без вывода ошибок, повтор в общем окне, полный сбой с повтором, истечение срока и PDF. Сопоставить frontend со Stitch, проверить PDF, доступ без регистрации, отсутствие ИИ/платных функций и раскрытия диагностики.

**Готово, когда:** все требования подтверждены, unit/integration/e2e и обязательные CI-проверки зелёные для последней версии, нет дефектов, нарушающих согласованный объём. Все API/процессы имеют актуальную документацию и Mermaid-диаграммы последовательностей. После слияния последнего PR локальная `main` обновлена; запуск продукта не объявляется выполненным до фактической проверки опубликованного окружения.

## Правила исполнения плана

- Перед задачей прочитать её зависимости и актуальную документацию. Завершённая задача означает выполненные критерии, проверки и влитый PR; один коммит сам по себе не меняет статус на «готово».
- Каждая задача выполняется в отдельной ветке от актуальной `main`; в PR указываются ID задачи/требований, результат, проверки и ограничения. После зелёного пайплайна и необходимых согласований — слияние, переключение на `main` и `git pull --ff-only origin main`.
- API, процессы, OpenAPI и Mermaid-диаграммы последовательностей обновляются вместе с кодом. Документирование не откладывается в последнюю задачу. Отдельный файл отчёта о проверках не создаётся: результаты — в PR.
- Тесты добавляются в задачах реализации, итоговая приёмка не заменяет их. Проверки устойчивости выбираются по риску, без обязательного перебора всех отказов интеграционными тестами.
- Сохранять DRY/KISS, переиспользовать выбранные библиотеки, токены, shared UI, модель отчёта и шаблоны. Не добавлять зависимости для несогласованных функций.
- Обновлять статусы и ссылки на PR в этом файле по факту. Если задача требует нескольких PR, явно разделить её на подзадачи с зависимостями; не помечать целую задачу завершённой по частичному результату.
- При изменении требований обновить этот план и связанные решения. Согласование плана не заменяет согласование дизайна и правовой методики; уже утверждённые продуктовые решения не пересогласовываются без изменения их содержания.
