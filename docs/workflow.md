# Процесс разработки для ИИ-агента

## Общие правила

Разработка каждой фичи проходит этапы последовательно:

1. Полный сбор требований и согласование с заказчиком.
2. Подготовка дизайна в Stitch и согласование с заказчиком, если этап требуется для задачи.
3. Полная реализация frontend, backend и всех уровней тестов.
4. Проверка реализации на соответствие требованиям и дизайну.

Не начинай реализацию до согласования требований и, когда этап дизайна требуется, дизайна. Для небольших изменений или задач без изменений UI создание дизайна в Stitch необязательно. Кратко укажи причину пропуска этапа в описании PR или `decisions.md`; отдельное разрешение на пропуск не требуется. Для существенных изменений UI этап обязателен.

Явное согласование заказчика должно относиться к конкретной версии артефактов. Молчание, собственное предположение агента и техническая готовность не заменяют согласование. Если согласование уже получено для актуальной версии, повторно запрашивать его не нужно.

Документируй фичу в `docs/features/<feature-id>/`:

| Файл | Содержание |
| --- | --- |
| `requirements.md` | Текущее поведение, сценарии, требования, критерии приёмки, границы и открытые вопросы |
| `design.md` | Если этап дизайна требуется: ссылки и идентификаторы Stitch, экраны и состояния, HTML/CSS, результаты изучения дизайна |
| `decisions.md` | Решения, изменения объёма, версии и согласования с датами и ссылками на сообщения |

Назначай требованиям устойчивые идентификаторы, например `BR-001` для бизнес-требований и `NFR-001` для нефункциональных. Новые вопросы и изменения фиксируй до продолжения зависимой работы.

Результаты тестов, проверки требований и визуального сравнения указывай в описании PR. Отдельный файл отчёта не создавай.

## Ветки и Pull Request

1. Каждую задачу, включая документацию и небольшие исправления, выполняй в отдельной ветке от актуальной `main`. Не коммить и не отправляй изменения напрямую в `main`.
2. Перед новой задачей проверь рабочее дерево. Сохрани текущую работу в её ветке, не удаляя и не перезаписывая чужие изменения. Переключись на `main`, выполни `git fetch origin` и `git pull --ff-only origin main`, затем создай ветку с понятным именем, например `feat/site-check`, `fix/report-status` или `docs/development-workflow`.
3. Делай связанные с задачей коммиты, выполни локальные проверки и отправь ветку в `origin`. Открой Pull Request с целевой веткой `main`.
4. В описании PR укажи проблему, результат изменений, ссылки на требования и дизайн, результаты проверок и ограничения. Для небольших изменений документации достаточно краткого описания без отдельного комплекта документов фичи.
5. Дождись завершения пайплайна для последнего коммита PR: все обязательные CI-проверки должны быть зелёными. Отсутствующий пайплайн, проверки в ожидании, ошибки и отменённые запуски не считаются успешным результатом. Если CI ещё не настроен, настрой его в рамках соответствующей задачи до слияния.
6. При ошибках исправь причины в этой же ветке, отправь изменения и снова дождись зелёного пайплайна. После новых коммитов или разрешения конфликтов проверяй результат для обновлённого PR, а не прежней версии.
7. Сливай PR в `main` только после выполнения критериев готовности, зелёного пайплайна и обязательных согласований или ревью, заданных репозиторием. Не обходи защиту веток и не используй принудительное слияние.
8. После подтверждённого слияния PR проверь рабочее дерево, переключись на `main` и обнови её: `git switch main`, затем `git pull --ff-only origin main`. Если локальной `main` ещё нет, сначала создай её с отслеживанием `origin/main`: `git switch --track origin/main`.
9. Убедись, что локальная `main` соответствует `origin/main`. Следующую задачу начинай в новой ветке. Если обновление невозможно из-за локальных изменений или расхождения истории, сохрани работу и устрани причину без `reset --hard` и принудительной отправки в `main`.

## 1. Полный сбор требований

### Действия

1. Изучи код, документацию, тесты и текущие пользовательские сценарии. Если функционал отсутствует, явно зафиксируй это.
2. Уточни у заказчика цели, пользователей, сценарии, входные и выходные данные, ограничения, исключения и ожидаемые ошибки.
3. Опиши бизнес-правила и измеримые критерии приёмки для каждого требования. Раздели согласованный объём, исключения и предложения.
4. Определи нефункциональные требования: безопасность, доступность интерфейса, производительность, хранение данных и эксплуатацию в необходимом для фичи объёме.
5. Для правовых проверок изучи актуальные официальные источники. Запиши нормативный акт, статью/пункт, ссылку, редакцию, дату проверки, применимость и ограничения вывода. Не подменяй правовые основания предположениями.
6. Уточняй требования до полного понимания: не должно оставаться вопросов, влияющих на объём, поведение, критерии приёмки или дизайн.
7. Представь заказчику конкретную версию `requirements.md` и зафиксируй его явное согласование в `decisions.md`.

### Условие завершения

Все требования понятны, проверяемы и согласованы заказчиком. Вопросы, влияющие на реализацию фичи, закрыты. После этого можно перейти к дизайну или непосредственно к реализации, если дизайн для задачи необязателен.

## 2. Подготовка дизайна в Stitch

Этот этап обязателен для существенных изменений UI. Для небольших изменений или задач без изменений UI его можно пропустить по общим правилам выше. Далее описаны действия для задач, которым дизайн необходим.

### Действия

1. Обязательно используй Stitch MCP для создания дизайн-борда фичи. Сохрани ссылку, идентификаторы проекта/борда и экранов в `design.md`.
2. Подготовь все согласованные пользовательские сценарии и состояния: начальное, загрузка, успех, пустой результат, ошибки и ограничения доступа, где применимо.
3. Определи необходимые размеры экранов, адаптивное поведение, навигацию, компоненты, типографику, цвета, отступы и состояния взаимодействия.
4. Получи и изучи HTML/CSS кода дизайна через Stitch MCP до реализации. Сохрани доступный экспорт в `docs/features/<feature-id>/design/` либо ссылку на версионированный экспорт. Зафиксируй, как структура, стили, ресурсы и поведение будут перенесены в приложение.
5. Проверь полноту дизайна относительно требований. Если экспорт не отражает нужное состояние или адаптивность, уточни дизайн и зафиксируй решение.
6. Представь заказчику конкретную версию дизайн-борда со всеми существенными экранами и состояниями. Сохрани явное согласование и идентификаторы согласованной версии в `decisions.md`.

Если Stitch MCP недоступен или не позволяет получить необходимый артефакт, зафиксируй препятствие и сообщи заказчику. Не заменяй инструмент самостоятельно и не начинай зависимую реализацию.

### Условие завершения

Дизайн-борд создан через Stitch MCP, покрывает требования и согласован заказчиком. HTML/CSS получены и изучены. Есть однозначная версия макета для последующего сравнения. Если этап пропущен, причина зафиксирована.

## 3. Реализация

### Действия

1. На основе согласованных требований определи архитектуру и стек, если они ещё не выбраны; зафиксируй решения и необходимые изменения зависимостей.
2. Полностью реализуй frontend в объёме задачи, включая адаптивность, состояния и обработку ошибок. Если есть согласованный дизайн, следуй ему и изученному HTML/CSS; для небольших изменений без нового макета используй существующие компоненты и стили.
3. Полностью реализуй backend: бизнес-правила, API, обработку ошибок, хранение данных и интеграции в согласованном объёме. Зафиксируй контракты API, если фича их вводит или меняет.
4. Соедини frontend с рабочим backend. Тестовые подмены допустимы в тестах, но не являются завершённой продуктовой интеграцией.
5. Добавь и выполни все уровни тестов:
   - **Unit:** бизнес-правила, условия применимости проверок, преобразования данных и граничные случаи.
   - **Integration:** взаимодействия API, хранилища, модулей и внешних интеграций, включая ошибки и ограничения доступа.
   - **E2E:** критические пользовательские сценарии через frontend и backend, включая успешный результат и значимые ошибки.
6. Сохрани безопасные фикстуры, инструкции подготовки тестового окружения и точные команды запуска. Внешние зависимости тестов и границы подмен должны быть описаны.
7. Выполни доступные обязательные проверки проекта: сборку, статический анализ, проверку типов и тесты. Зафиксируй команды, окружение и результаты в описании PR.
8. Обнови документацию: настройку, запуск, конфигурацию, API и ограничения по мере появления соответствующих частей приложения.

### Условие завершения

Весь согласованный функционал frontend и backend реализован и связан. Unit-, integration- и e2e-тесты проходят, обязательные проверки проекта выполнены. Для требований есть ссылки на реализацию и тесты. После этого можно переходить к итоговой проверке.

## 4. Проверка соответствия реализации

### Бизнес-требования

Проверь все критерии приёмки, включая негативные сценарии и ограничения применимости правовых проверок. В описании PR кратко свяжи требования с реализацией и проверками, укажи фактические результаты и ссылки на тесты. Для результата, требующего ручной оценки, интерфейс и отчёт должны явно отражать это состояние.

### Соответствие дизайну

Если для задачи есть согласованный макет Stitch, выполни сравнение ниже. Для небольших изменений без нового макета проверь сохранение существующего оформления и поведения; для задач без изменений UI визуальное сравнение не требуется.

1. Сопоставь реализацию с согласованной версией макета Stitch на одинаковых размерах экрана и данных.
2. Проверь каждый предусмотренный экран и состояние: расположение, размеры, типографику, цвета, отступы, ресурсы, адаптивность и взаимодействия.
3. Приложи скриншоты реализации и ссылки на соответствующие макеты к PR; там же запиши результаты сравнения.
4. Устрани все найденные расхождения. Изменение согласованного дизайна сначала внеси в Stitch и согласуй с заказчиком, затем обнови реализацию и проверки.

### Критерии готовности фичи

- [ ] Текущий функционал изучен, требования полностью собраны и согласованы.
- [ ] Дизайн-борд создан через Stitch MCP и согласован, HTML/CSS изучены; либо этап обоснованно пропущен для небольшого изменения или задачи без изменений UI.
- [ ] Frontend и backend полностью реализованы и интегрированы.
- [ ] Unit-, integration- и e2e-тесты проходят; команды и результаты сохранены.
- [ ] Выполнение всех бизнес-требований проверено; результаты указаны в PR.
- [ ] Реализация полностью соответствует согласованному макету Stitch, если он есть; результаты визуальной проверки приложены к PR для изменений UI.
- [ ] Правовые проверки имеют официальные источники, условия применимости и ограничения.
- [ ] Документация актуальна; нет незакрытых дефектов, нарушающих требования или дизайн.
- [ ] Изменения находятся в отдельной ветке, PR направлен в `main`, пайплайн для последнего коммита зелёный.

В итоговом отчёте дай ссылки на реализацию, требования, дизайн и результаты тестов. Не объявляй фичу завершённой, если обязательный пункт не выполнен: явно укажи оставшуюся работу и причину.

## Изменение требований и возврат к этапам

Если обнаружена неоднозначность или изменился объём, вернись к сбору требований, обнови документы и получи согласование затронутых решений. Для существенных изменений интерфейса обнови дизайн через Stitch MCP и согласуй новую версию; небольшие изменения и задачи без изменений UI подпадают под исключение выше. После изменений повтори затронутые тесты и проверки соответствия; не используй устаревшее согласование как разрешение на новую версию.
