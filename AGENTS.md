# Инструкции для ИИ-агента

Проект — сервис проверки сайтов на соответствие применимым требованиям законодательства РФ и Роскомнадзора. Стек, архитектура, основные решения MVP и первый набор проверок согласованы. Приложение ещё не реализовано; подробные требования и правовую методику нужно завершить.

## Перед началом работы

1. Прочитай [описание проекта](docs/project.md), [утверждённый стек](docs/tech-stack.md), [требования к коду](docs/code-standards.md), [требования к документации](docs/documentation.md) и обязательный [процесс разработки](docs/workflow.md).
2. Изучи существующий код, документацию, тесты и более локальные `AGENTS.md`, если они появились.
3. Определи текущий этап задачи и найди зафиксированные согласования заказчика. Не считай молчание согласованием.
4. Для MVP прочитай [требования](docs/features/site-audit/requirements.md), [решения](docs/features/site-audit/decisions.md), [план работ](docs/mvp-plan.md) и [каталог проверок](docs/violations.md). Сначала реализуется согласованный заказчиком этап UI/UX-прототипа с фейковой проверкой; настоящая проверка — после оценки интерфейса. Согласованные решения не требуют повторного выбора; открытые вопросы и юридическую готовность правил не считай закрытыми.

## Обязательные правила

- Веди документацию проекта в `docs/`, исходный код — в `src/`.
- Пиши документацию и общайся с заказчиком на русском языке, если он не попросил иначе.
- Следуй утверждённому стеку: React и TypeScript, ASP.NET Core, MediatR, EF Core и PostgreSQL; используй Clean Architecture и Vertical Slice. Полный перечень решений — в `docs/tech-stack.md`. Фоновые процессы пока не имеют выбранного механизма реализации.
- Следуй DRY и KISS: сначала ищи возможности переиспользования, пиши минимальный необходимый код, вводи абстракции по конкретной потребности.
- Backend обязан сохранять бизнес-инварианты при сбоях и работе нескольких экземпляров. Учитывай транзакции, конкуренцию, повторы и восстановление; критичное состояние нельзя хранить только в памяти экземпляра.
- Frontend обязан использовать дизайн-систему Stitch и shared-компоненты с применимыми состояниями в Storybook. Исключение для небольших изменений не отменяет соблюдение дизайн-системы.
- До реализации фичи собери и согласуй требования. Для существенных изменений UI подготовь и согласуй дизайн в Stitch через Stitch MCP. Для небольших изменений или задач без изменений UI новый дизайн в Stitch необязателен; кратко зафиксируй причину пропуска этапа.
- Когда этап дизайна необходим, обязательно используй Stitch MCP. Если MCP недоступен, сообщи о препятствии; не подменяй его другим инструментом самостоятельно.
- Если для задачи подготовлен дизайн в Stitch, изучи его HTML/CSS до реализации и используй их при проверке соответствия макету.
- Каждую задачу, включая изменения документации, выполняй в отдельной ветке от актуальной `main`. Изменения попадают в `main` только через Pull Request после зелёного пайплайна. После слияния переключись на `main` и обнови её через `git pull --ff-only origin main`. Подробности — в `docs/workflow.md`.
- Реализуй frontend и backend в полном согласованном объёме текущего этапа. Для первого UI/UX-прототипа заказчик прямо разрешил фейковую проверку: используй обозначенные демонстрационные данные и симуляцию без обращений к проверяемому сайту. Не выдавай их за готовые интеграции или настоящий аудит. Правовая методика и гарантии настоящего backend обязательны для рабочего MVP, но не блокируют этот прототип.
- Для фичи обязательны unit-, integration- и e2e-тесты. Объём проверок устойчивости определяй по риску; покрывать интеграционными тестами все случаи сбоев не требуется. Сохраняй команды запуска и результаты проверок; не отмечай непройденные или незапущенные проверки как успешные.
- Проверяй выполнение всех требований и визуальное соответствие согласованному дизайну, если он есть. Результаты проверок сохраняй в описании PR; отдельный файл отчёта не нужен.
- Не придумывай правовые требования. Для каждой правовой проверки фиксируй актуальный официальный источник, применимость и дату проверки источника. Отделяй автоматические результаты от случаев, требующих ручной оценки.
- Новые правовые проверки сначала добавляй в `docs/violations.md`. Реализуй их постепенно; наличие строки в каталоге не означает готовую методику или выполненную проверку. Не суммируй штрафы без подтверждённых оснований и не превращай технический сигнал в доказанное нарушение.
- Обновляй документацию вместе с изменением функционала. Не включай секреты и реальные персональные данные в репозиторий, примеры и тестовые фикстуры.
- Документируй все API и фоновые процессы в `docs/` с Mermaid-диаграммами последовательностей. API-контракты описывай через OpenAPI. Обновляй документацию в том же PR, что и реализацию.
- Не меняй согласованный объём или дизайн самостоятельно: верни затронутые решения на согласование и зафиксируй изменения.

## Документация задачи

Для каждой фичи создавай `docs/features/<feature-id>/` с файлами, описанными в `docs/workflow.md`. Переноси туда решения и ссылки на согласования из переписки, не приписывая заказчику одобрение, которого он не давал.

Подготовка структуры репозитория и изменение документации сами по себе не означают начало реализации продукта. При переходе к продуктовой фиче пройди все этапы процесса.
